阶段 2 · 少算、少搬

gather_last：只算最后一行

prefill 的 lm_head 从 T 行降到 1 行。

本步目标lm_head 只对每条序列的最后一个 token 算。prefill 512 个 token 时，logits 从 512 行降到 1 行。

原理

prefill 算出来的 logits 大部分没人要

src/models/qwen3.zig 起点（你现在的代码）
    // input_ids, embedding, final_norm, lm_head 未分配 layer，默认在 CPU 执行
    fn forward(self: *Self, input_ids: *Tensor) !*Tensor {
        var x = try self.embed.forward(input_ids);

        for (self.layers.items) |*qwen3_layer| {
            x = try qwen3_layer.forward(x);
        }

        const fx = try self.final_norm.forward(x);
        const logits = try self.lm_head.forward(fx);

        return logits;
    }
};

final_norm 的输出是 [1, T, hidden]，lm_head 把它整个乘上词表矩阵，得到 [1, T, 151936]。但采样只看最后一行：前 T-1 行预测的是 prompt 里已经有的 token。

以 S1 的 512 token prefill 为例，多算的东西：

起点只算最后一行
lm_head 的 GEMM512 × 1024 × 151936，约 159 GFLOP1 × 1024 × 151936，约 0.31 GFLOP
logits 占的激活内存148 MiB0.3 MiB
回拷到 host148 MiB0.3 MiB

decode 时 T = 1，本来就只有一行，这一步对 ITL 没有影响。它改善的是 TTFT 和激活内存。

为什么需要第二个动态维

图里原来只有一个动态维 DYN（-1），执行前统一填成本步的 token 数 T。gather 之后的张量行数不再是 T，而是序列数 S（现在 S = 1，第 19 步之后可以是 256）。所以要第二个标记 DYN_S（-2）：

final_norm[1, T, 1024]
→
gather_last[1, S, 1024]
→
lm_head[1, S, 151936]
→
sample[1, S]（第 09 步）

取哪一行由元数据的 last[S] 决定，第 04 步的 fillMeta 已经在填了：last[s] = 序列 s 本步最后一个 token 在 T 里的行号。

kernel 就是按行拷贝，和 embedding 一个写法：

backend/cuda/memcpy.cu（加到 llmgen 的 memcpy.cu 末尾） lab 参考（3090 实测过）
// ------------------------------------------------------------------
// gather_rows: out[s] = x[idx[s]]
// ------------------------------------------------------------------
__global__ void gather_rows_kernel(bf16x8 *out, const bf16x8 *x, const int *idx, int H8) {
    int s = blockIdx.x;
    long src = idx[s];
    for (int i = threadIdx.x; i < H8; i += blockDim.x) out[(long)s * H8 + i] = x[src * H8 + i];
}

extern "C" void cuda_gather_rows(cuda_bf16_t *out, const cuda_bf16_t *x, const int *idx, int S, int H) {
    if (S <= 0) return;
    gather_rows_kernel<<<S, 128, 0, g_cuda_stream>>>((bf16x8 *)out, (const bf16x8 *)x, idx, H / 8);
}

//! module/serving.zig -- 服务引擎专用的图尾部节点:gather_last(第 08 步)和 sample(第 09 步)
const std = @import("std");
const Tensor = @import("../Tensor.zig");
const base = @import("base.zig");

/// x [1, T, H] → [1, S, H]:每条序列取它本步最后一个 token 的那一行。
/// 取哪一行在执行期由元数据的 last[S] 决定。
pub fn gatherLast(allocator: std.mem.Allocator, x: *Tensor, name: []const u8, layer_id: i32) !*Tensor {
    const t = try base.newTensor(allocator, .{
        .name = name,
        .layer_id = layer_id,
        .data_type = x.data_type,
        .tensor_type = .TENSOR_TYPE_ACTIVATION,
        .op_type = .OP_TYPE_GATHER_LAST,
        .src = base.srcs(&.{x}),
        .dims = .{ 1, base.DYN_S, x.dims[2], 0 },
    });
    base.computeStrides(t);
    return t;
}

pub const GatherLastImpl = struct {
    pub fn execute(_: i32, out_tensor: *Tensor) !void {
        const x = out_tensor.src[0].?;
        const s = &common.g_step;
        const row = @as(usize, @intCast(s.hidden)) * x.data_type.size();
        const last: [*]const i32 = @ptrCast(@alignCast(s.last.?));
        for (0..@intCast(s.n_seq)) |i| {
            const from = @as(usize, @intCast(last[i])) * row;
            @memcpy(out_tensor.data.?[i * row ..][0..row], x.data.?[from..][0..row]);
        }
    }
};

5建池时别把 [S, vocab] 当成 [max_seq, vocab]

调度器估算激活池容量时把所有负维都填成 max_seq。logits 这一个张量就要 1024 × 151936 × 2 = 297 MiB，起点的激活池 341 MiB llmgen 起点实测 基本是被它撑起来的。

对 llmgen 的预期

TTFT：S1 的 prefill 少算 511 行 lm_head、少回拷 148 MiB。回拷走的是普通内存，速率通常只有几 GB/s，光这一项就是几十毫秒；GEMM 那 159 GFLOP 在 3090 的 tensor core 上也要几毫秒。预期 S1 的 TTFT 降 30–80 ms 推算。目标 lab 整个 TTFT 才 13.47 ms，说明这部分在目标形态里完全不存在。

内存：激活池从约 341 MiB 降到 64 MiB 的下限（单层最大激活远小于 64 MiB）。

ITL：不变。
