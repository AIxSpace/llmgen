阶段 6 · 收尾

附录：回退开关与排错

出问题时怎么二分。

本步目标把一路上留下的回退开关汇总成一张表，给出出问题时的二分顺序。这一页是工具书，不改代码。

回退开关

每个开关都把某一项优化关掉，退回到“改之前”的行为。默认值都是优化开启，开关关闭时没有额外开销。

开关关掉的是加在哪一步用途
--eagerCUDA Graph：decode 步逐 kernel 发射17排查“回放和录制不一致”；量 Graph 的收益
--sync-each异步：每个节点后同步一次07排查漏改 stream 的偶发错误；量同步的代价
--debug-sync同上，另外打印节点名、检查 CUDA 错误本页定位哪个节点的 kernel 发射失败
SV_GEMV_MAX_M=0自写 GEMV：Linear 全走 cuBLAS12量 GEMV 的收益；怀疑 GEMV 算错时对照
SV_GEMV_MAX_M=8把 GEMV 的阈值从 2 调到 812看阈值过大的代价（S4）
SV_ATTN_PART=100000split-K：每条序列只切 1 段13量 split-K 的收益
--policy chunkedprefill_first 调度20在线负载下保护 decode 的 ITL
--kv-blocks N按显存比例自动算 KV18对齐 KV 容量的对比；复现抢占
--pass-tokens N单趟 token 上限（默认 8192）19激活区大小和 KV 容量的取舍
LLMGEN_PROFILE=1（不是回退）算子级计时，强制 eager + 逐算子同步02看各类算子的耗时占比
SV_* 开关在第一次调用时读一次它们是 .cu 里的 static 变量，进程启动后第一次用到时读环境变量并缓存。CUDA Graph 录制时读到的值会被录死。所以必须在启动进程之前设好，中途改无效。

出错时的二分顺序

症状是“输出不对”时，按下面的顺序缩小范围。每一步都只换一个变量。

终端 命令
# 1. 先确定是不是 CUDA Graph 的问题
./zig-out/bin/llminfer chat "中国的首都是哪里？" 64 --eager

# 2. 是不是异步 / stream 的问题
./zig-out/bin/llminfer chat "中国的首都是哪里？" 64 --sync-each

# 3. 哪个节点开始出错(每个节点后同步 + 检查 CUDA 错误 + 打印节点名)
./zig-out/bin/llminfer chat "中国的首都是哪里？" 64 --debug-sync 2>&1 | tail -30

# 4. 单个 kernel 对不对
make llmgen-cuda-test

# 5. 和目标 lab 逐 token 比
<Genllm>/study/zig-out/bin/lab-module-serving-unfused chat "中国的首都是哪里？" 64 | grep "token ids"
观察结论去哪查
--eager 对，默认错CUDA Graph 录进了会变的东西第 17 步“参数是录死的”那张表，逐项对
--sync-each 对，--eager 错执行顺序问题：有 kernel 或拷贝不在 g_cuda_stream 上第 07 步的 grep
--sync-each 也错，每次错得一样某个 kernel 或元数据算错了--debug-sync + kernel_test
每次错得不一样读了未初始化的显存，或两个活着的激活重叠第 16 步；padding 行（第 17 步）
CUDA 错，--device cpu 对执行层和元数据没问题，是某个 CUDA kernel 或它的 Impl 传参CPU 是活参考：C4 的逐 token 对拍；再用 kernel_test 定位
CPU 和 CUDA 都错，且错得一样执行层：元数据、块表、图结构fillMeta、BlockManager
单请求对，批处理错序列边界：cu_q / last / 块表的行偏移第 19 步“8 份相同 prompt”的检查
前 16 个 token 对，之后错块表：第 17 个 token 进第二块第 06 步
短 prompt 对，长 prompt 错prefill 的 tile（> 64 token）或多趟切分（> 8192 token）第 14、19 步
kernel_test 全过，端到端错kernel 没问题，是 Impl 传参或元数据对着 lab 的 backend/cuda/*.zig 逐个比参数

--debug-sync 在 lab 里是这样实现的，搬到 llmgen 的 executorTensor 里即可：

executor.zig · executeTensor（--debug-sync / --sync-each） lab 参考（3090 实测过）
    fn executeTensor(self: *Executor, node: *Tensor) !void {
        // 视图节点(拆头 / attn_tr 的 reshape)与根共享地址(见 plan.zig), 不发 kernel
        if (node.type == .TENSOR_TYPE_VIEW) return;
        const dev_id = self.devIdOf(node);
        // 读写分页 KV 的节点(本 lab 只有注意力: 先写本步 k/v 再读):按本节点所在设备取对应 PagedAttentionManager.
        if (node.op_type == .OP_TYPE_PAGED_ATTN) {
            ops.setAttnMgr(self.mm.getAttentionManager(node.device, @intCast(dev_id)) orelse return error.NoAttentionManager);
        }
        try dispatchKernel(node, dev_id);
        if (self.cfg.sync_each) self.syncDevice();
        if (self.cfg.debug_sync) {
            self.syncDevice();
            std.debug.print("[debug] {s} ok\n", .{node.name});
            if (comptime opts.have_cuda) {
                if (self.device == .CUDA) cu.check(node.name) catch std.debug.panic("kernel 失败: {s}", .{node.name});
            }
        }
    }

终端 命令
# 时间线(每个 prefill / decode 步一个 NVTX 区间, 需要把 lab 的 cuda_nvtx_push / pop 也搬过来)

ncu --kernel-name gemv_kernel --launch-count 1 ./zig-out/bin/llminfer chat "你好" 8 --eager
观察可能的原因
cuda_api_sum 里有 cudaMalloc / cudaFree / 同步 cudaMemcpy热路径上还有没清掉的分配或拷贝（阶段 1）
cudaLaunchKernel 次数 ≈ 步数 × 500CUDA Graph 没生效：看 graph_steps，是不是被 profile / sync-each 强制 eager 了
cudaStreamSynchronize 次数远大于步数有地方多同步了：cuda_h2d（同步版）被用在了热路径上
kernel 表里 gemv_kernel 平均耗时明显大于 13.3 µsGPU 被别的进程占着，或者没升频（没预热）
S3 的 steps 比目标多很多抢占（preemptions > 0）或单趟上限太小
ITL p99 远大于 meanprefill_first 下大 prefill 挡住了 decode；或 host 上有偶发的慢操作（分配器、打印）
