阶段 5 · 连续批处理

序列级块表与 KV 预算

拆开 max_seq_len，KV 按显存比例分。

本步目标KV cache 的容量从“写死 1024 个 token”改成“显存剩多少给多少”。原来一个 max_seq_len 同时管着四件不同的事，这一步把它们拆开。批处理需要的容量和参数就齐了。

原理

一个 max_seq_len 管了四件事

它现在决定实际应该由谁决定目标值
单条序列最长多少 tokenmax_model_len：块表的列数、位置的上限4096
一步前向最多多少 tokenmax_tokens：激活 token 区的大小8192
一步最多多少条序列max_num_seqs：序列区、元数据、CUDA Graph 桶256
KV cache 能存多少 tokennum_kv_blocks × block_size：所有序列共享的池子按显存算，约 17.6 万

单序列时这四个数相等，混在一起没问题。批处理时它们差着数量级：256 条序列共享 17.6 万 token 的 KV，但每步只有 256 个 token 进前向。

KV 是一个共享的块池

第 06 步之后，KV 的布局是每层一整块 [块][kv_head][slot][hd]，块的归属由 BlockManager 管：

block_manager.zig lab 参考（3090 实测过）
pub const BlockManager = struct {
    alloc: Alloc,
    block_size: usize,
    num_blocks: usize,
    free: std.ArrayListUnmanaged(i32) = .empty, // 空闲块栈

    pub fn init(alloc: Alloc, num_blocks: usize, block_size: usize) !BlockManager {
        var self = BlockManager{ .alloc = alloc, .block_size = block_size, .num_blocks = num_blocks };
        try self.free.ensureTotalCapacity(alloc, num_blocks);
        var i: usize = num_blocks;
        while (i > 0) {
            i -= 1;
            self.free.appendAssumeCapacity(@intCast(i)); // 栈顶是 0 号块
        }
        return self;
    }

    pub fn deinit(self: *BlockManager) void {
        self.free.deinit(self.alloc);
    }

    pub fn numFree(self: *const BlockManager) usize {
        return self.free.items.len;
    }

    /// 让 seq 的块表至少覆盖前 n 个 token. 块不够返回 false(不做部分分配).
    pub fn ensure(self: *BlockManager, seq: *Sequence, n: usize) !bool {
        const need = Sequence.blocksFor(n, self.block_size);
        const have = seq.block_table.items.len;
        if (need <= have) return true;
        if (need - have > self.free.items.len) return false;
        try seq.block_table.ensureUnusedCapacity(self.alloc, need - have);
        for (0..need - have) |_| seq.block_table.appendAssumeCapacity(self.free.pop().?);
        return true;
    }

    pub fn canEnsure(self: *const BlockManager, seq: *const Sequence, n: usize) bool {
        const need = Sequence.blocksFor(n, self.block_size);
        const have = seq.block_table.items.len;
        return need <= have or need - have <= self.free.items.len;
    }

    /// 释放 seq 的全部块(完成或被抢占).
    pub fn deallocate(self: *BlockManager, seq: *Sequence) void {
        var i = seq.block_table.items.len;
        while (i > 0) {
            i -= 1;
            self.free.appendAssumeCapacity(seq.block_table.items[i]);
        }
        seq.block_table.clearRetainingCapacity();
        seq.num_computed_tokens = 0;
    }
};

一个空闲块的栈。序列需要更多块时 ensure 从栈顶取；序列结束或被抢占时 deallocate 整条归还。块号在所有层通用：拿到块 7，就是每一层 K 和 V 的第 7 块都归你。

所以“KV 容量”就是总块数。一个 token 在所有层的 K + V 一共占：

28 层 × 2（K、V）× 8 个 kv 头 × 128 × 2 B = 114688 B ≈ 112 KiB

起点给了 1024 个 token，112 MiB llmgen 起点实测。一块 3090 有 24 GB。

按显存比例分

vLLM 和 nano-vllm 的做法：给一个比例（默认 0.9），总显存 × 比例，减去已经用掉的、权重、激活，剩下的全切成 KV 块。

    max_tokens: usize = 1, // 单趟前向最多 token 数 T(激活区按它分配)
    max_model_len: usize = 1, // 单条序列最长 token 数(块表列数 / RoPE 表长度)

/// KV 预算里给 CUDA Graph 等杂项留的余量(实测 < 20MB).
const KV_RESERVE: usize = 32 << 20;

块大小

块越大，块表越短、寻址越省；但每条序列最后一块平均浪费半块。block 16 时每条序列平均浪费 8 个 token；block 256 时浪费 128 个。nano-vllm 用 256，lab 用 16。lab 实测两者吞吐相同，16 在容量紧张时抢占更少（见第 20 步的表）。

对拍验证

单请求的结果不变：greedy 输出和上一步逐 token 相同。启动日志里确认 KV 池的大小：

  • kv_cache 池应该是 19 GB 左右；
  • 用 nvidia-smi 看进程占用，约 21.7 GB；
  • 启动时间会变长一点：要录 20 个 CUDA Graph 桶。
3090 上还有别的进程时预算按 total_memory × 0.9 - used_memory 算。有别的进程占着显存（比如 lab 提到的 llama-server），KV 会相应变小，甚至报 NoMemoryForKvCache。压测前先清干净。

CPU 同步

这一步 CPU 后端要做的事必须同步改。“总显存 × 比例”的预算公式不能用在 CPU 上（CPU 的总内存在 backend.zig 里是写死的 16 GB，会一口气申请十几 GB）。CPU 给固定块数：512 块 = 8192 token，约 0.9 GB；单趟 token 上限 2048。 去看 →

对 llmgen 的预期

这一步不改单请求的速度。它决定的是能同时放多少条序列。

S3 的 256 条请求输入加输出共 27.7 万 token。KV 有 17.6 万时，靠序列陆续结束、块陆续归还，全程 0 次抢占；KV 减半到 8.6 万时，抢占 157 次，吞吐降 17%，平均 TTFT 从 1.3 秒涨到 6.9 秒 消融实测。

起点的 1024 token 连 S2 的一条请求（最长 512 + 512）都只能勉强放下。
