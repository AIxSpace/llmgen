CPU 支线

CPU：执行层与命令行

KV 预算、加载、--device，以及最终的 CPU / CUDA 对拍。

本步目标主线阶段 4–6（激活规划、CUDA Graph、KV 预算、批处理、命令行、加载）在 CPU 上各自意味着什么。大部分不用动；要动的是 KV 预算的缺省值、权重加载和 --device。

原理：哪些和设备无关，哪些有关

主线在 CPU 上要做的事
16 激活规划完全一样。规划的是“每行偏移”，基址是 CPU 池里的地址无
17 CUDA Graph没有。每步都是 eager：逐节点派发，同步执行无（enforce_eager 已经对非 CUDA 设备恒为真）
18 KV 预算不能按“总显存 × 比例”算给固定块数
19 批量前向完全一样。变长打包、多趟切分都是 host 逻辑无
20 调度完全一样无
21 加载不需要 pinned 暂存区，磁盘直接读进池改 CPU 分支
21 CLI多一个 --device加选项

padding 行（主线第 17 步）只在回放 CUDA Graph 时出现，CPU 上 Sn 恒等于实际序列数，fillMeta 的 padding 循环不执行。

先过一遍执行层

主线各步给出的执行层代码已经带了设备判断。CPU 支线做到这里，值得对着下面的清单把 executor.zig 通读一遍，确认没有漏网的 CUDA 调用：

src/executor.zig：检查清单 示意，不落地
// 执行层里所有碰 CUDA 的地方, 都要带这两个条件之一(主线各步的代码已经是这样):
if (opts.have_cuda and self.input_tensor.device_type == .CUDA) { ... }   // 运行时在 CPU 上就跳过
if (comptime opts.have_cuda) { ... }                                     // 纯 CPU 构建时这段不编译

// 逐项:
//   allocMeta      CPU: meta_host = 池里那块缓冲本身;不切 part_o / part_ml / sample_scratch;不分配 out_host
//   uploadMeta     CPU: 什么都不做(fillMeta 已经直接写进池里了)
//   fetchOutAt     CPU: 直接把输出节点的 data 当 [*]const i32 读
//   executorTensor CPU: 不同步
//   init           CPU: enforce_eager = true, 不调 captureGraphs
//   deinit         CPU: 不调 cuda_host_free / cuda_graph_destroy
最容易漏的一处主线第 09 步的 fetchOut 里，CUDA 分支之后是 cuda.CudaContext.instance().sync()。如果把 sync 写在分支外面，纯 CPU 构建会编译不过（cuda 是空结构），带 CUDA 构建跑 CPU 时会无谓地初始化 CUDA 上下文。

KV 预算（主线第 18 步）

主线第 18 步的预算公式是 total_memory × gpu_memory_utilization − used − 权重 − 激活。llmgen 的 CPUBackendProvider 把 CPU 的总内存写死成 16 GB（backend/backend.zig），按这个公式会一口气申请十几 GB 的 KV。

lab 的做法是 CPU 不自动算，给保守的固定值：

main.zig lab 参考（3090 实测过）
const HOST_KV_BLOCKS: usize = 512; // × 16 token × 28 层 × K/V × 8 头 × 128 × 2B ≈ 0.9 GB
const HOST_PASS_TOKENS: usize = 2048;
main.zig · 按设备给缺省值 lab 参考（3090 实测过）
    const on_cuda = dev_info.device == .CUDA;
    const pass_tokens = o.pass_tokens orelse if (on_cuda) 8192 else HOST_PASS_TOKENS;
    const kv_blocks = o.kv_blocks orelse if (on_cuda) 0 else HOST_KV_BLOCKS;
CUDA 缺省CPU 缺省为什么
KV 块数按显存比例自动算（约 1.1 万块）512 块 = 8192 token，约 0.9 GB主机内存要留给系统和权重（1.2 GB）
单趟 token 上限81922048激活 token 区 = 21.5 KB × 上限。CPU 上一趟算 8192 个 token 也没有意义
max_num_seqs256256（序列区 75 MB）嫌大可以调小，序列区主要是每条序列一行 logits
src/llmgen.zig 改动对比
    const on_cuda = picked[0].device_type == .CUDA;    var graph_scheduler = GraphScheduler.init(allocator, compute_graph, .{        ...        .max_tokens = @max(pass_tokens, max_num_seqs),        .gpu_memory_utilization = 0.9,        // CPU 没有"显存比例"这回事:BackendInfo 里 CPU 的总内存是写死的 16 GB, 按比例算会申请十几 GB        .max_tokens = @max(if (on_cuda) pass_tokens else 2048, max_num_seqs),        .gpu_memory_utilization = 0.9,        .num_kv_blocks = if (on_cuda) 0 else 512, // 512 块 × 16 = 8192 token, 约 0.9 GB

权重加载（主线第 21 步）

主线第 21 步把 GGUF 改成只解析头部、权重留在磁盘。CUDA 要经一块 pinned 暂存区再 H2D；CPU 的池就是普通内存，直接 pread 进去，一次拷贝都不多：

manager.zig · loadOne：stage 为空就是 CPU lab 参考（3090 实测过）
                .bf16 => {
                    if (p.dtype != .GGML_TYPE_BF16) return error.WeightMustBeBf16;
                    const total = p.bytes();
                    const file_off = parser.dataOffset() + p.offset;
                    if (stage) |st| {
                        if (comptime !opts.have_cuda) unreachable;
                        // 分块: pread → pinned → H2D(同步), 暂存区只有 32MB
                        var done: usize = 0;
                        while (done < total) {
                            const chunk = @min(STAGE_BYTES, total - done);
                            const n = try parser.file.?.preadAll(st[0..chunk], file_off + done);
                            if (n != chunk) return error.ShortRead;
                            cu.cuda_h2d(dev_base + dst_off + done, st, chunk);
                            done += chunk;
                        }
                    } else {
                        const n = try parser.file.?.preadAll(dev_base[dst_off..][0..total], file_off);
                        if (n != total) return error.ShortRead;
                    }
                    dst_off += total;
                },

--device（主线第 21 步）

main.zig · pickDevice lab 参考（3090 实测过）
/// --device 给了就按名字找; 否则按 cuda > metal > cpu 挑第一台可用的.
fn pickDevice(devices: []const @import("backend/backend.zig").BackendInfo, want: ?[]const u8) ?@import("backend/backend.zig").BackendInfo {
    const T = @import("tensor.zig");
    const order = [_]T.Device{ .CUDA, .METAL, .CPU };
    for (order) |dev| {
        if (want) |name| {
            if (!std.ascii.eqlIgnoreCase(name, @tagName(dev))) continue;
        }
        for (devices) |d| {
            if (d.device == dev) return d;
        }
    }
    return null;
}

把 C1 里临时的 LLMGEN_DEVICE 换成命令行选项。缺省挑“最好的可用设备”（cuda > cpu），纯 CPU 构建时自然落到 CPU。--eager / --sync-each 以及 SV_* 开关在 CPU 上没有意义，解析但忽略。

最终验证（主线第 22 步）

zig build -Doptimize=ReleaseFast
./zig-out/bin/llminfer chat "中国的首都是哪里？" 64

# 3090:同一个二进制两个后端
./zig-out/bin/llminfer chat "中国的首都是哪里？" 64 --device cpu

# CPU 上的小规模批处理(S1–S4 对 CPU 太大, 自己造一个 4 条 × 32 → 32 的 workload)
./zig-out/bin/llminfer bench /tmp/tiny.json --device cpu --kv-blocks 512
  • 逐 token 对拍：--device cpu 和 --device cuda 的 greedy token id 相同。lab 的结果是 64 个 token 全部相同，mac 上的 CPU 也和 3090 上的 CUDA 相同 lab CPU 实测。
  • 批处理：CPU 上跑一个小 workload，8 份相同 prompt 的输出互相相同（主线第 19 步的检查），且和 CUDA 相同。
  • 速度：单请求 decode 和 lab 同量级。

主线第 22 步的 run_all.sh 对比的是 CUDA 的数字，不用加 CPU 列：S1–S4 在 CPU 上要跑很久，而且没有可比的对象（nano-vllm 没有 CPU 后端）。

对 llmgen 的预期

这一页没有速度上的改动。CPU 后端最终的位置：

  • 单请求 decode 约 20 tok/s，是 CUDA 的 1/20。瓶颈是内存带宽，不是代码。
  • 批处理在 CPU 上同样能提高吞吐（权重读一遍、多行输入共用），但 CPU 的算力不像 GPU 那样有大量富余，批到 4–8 之后就不再线性了 推算。
  • RSS：权重 1.2 GB + KV 0.9 GB + 激活几十 MB，约 2.2 GB。

它的价值是随处能跑、随时能对拍：mac 上开发执行层，CPU 当 CUDA 的参考，没有 GPU 的机器上也能演示。

常见错误

现象原因和处理
CPU 启动时申请十几 GB 内存 / 被 OOM 杀掉KV 按“显存比例”算了。CPU 要给固定的 num_kv_blocks。
纯 CPU 构建编译报 struct has no member named cuda_…执行层有 CUDA 调用没包在 if (opts.have_cuda …) 里。opts.have_cuda 是编译期常量，这样写的分支在纯 CPU 构建时不会被分析。
带 CUDA 构建跑 --device cpu 仍然初始化了 CUDADeviceManager 发现设备时会建 CUDA 上下文，这是预期的；但之后不应再有 CUDA 调用。
CPU 上 error.OutOfBlocks512 块只有 8192 token。长对话或批大了用 --kv-blocks 调大（每 512 块约 0.9 GB）。
CPU 和 CUDA 在带温度采样时输出不同采样的随机数相同，但 logits 有 f32 最后一位的差别时，Gumbel-max 可能选到不同的 token。只用 greedy 做逐 token 对拍。
CPU 加载比 CUDA 慢1.2 GB 权重要真的读进内存（CUDA 是读进暂存区再传走）。冷缓存时受磁盘速度限制。

检查点

  • --device cpu 和 --device cuda 的 greedy 输出逐 token 相同
  • CPU 上能跑小规模的 bench
  • 纯 CPU 构建（mac）能编译、能跑 chat 和 zig build test
