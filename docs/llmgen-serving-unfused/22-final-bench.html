最终对比

同一 workload、同一采样器，三个引擎跑一遍。

本步目标在同一块 3090、同一份 workload、同一个显存采样器下，把 llmgen、目标 lab、nano-vllm 三个引擎各跑一遍 S1–S4，出一张对比表。llmgen 对目标 lab 的比值落在 0.9–1.1 之间，就是做到了。

原理：怎么比才公平

做法为什么
workload三个引擎读同一份 JSON（token id，不是文本）不受 tokenizer 和 chat 模板差异影响
输出长度ignore_eos = True，每条请求固定 max_tokens三边输出 token 数严格相等，吞吐才可比
采样temperature = 0.6nano-vllm 不支持 greedy（温度必须 > 0）
prompt每轮不同nano-vllm 有 prefix cache，重复的 prompt 会命中缓存，不是同一份工作量
显存进程外 NVML 采样各引擎自报的口径不同
KV 容量默认都用 gpu_memory_utilization = 0.9；另跑一组“对齐 KV 容量”0.9 时各家实际分到的 KV 不同，会影响抢占次数
环境跑之前停掉其它占 GPU 的进程KV 预算按“总显存 − 已用”算
顺序同一场景三个引擎挨着跑，间隔 3 秒温度、频率状态尽量一致

#!/bin/bash
# 在 RTX 3090 上依次压测 module-serving-unfused / module-serving / nano-vllm(同一 workload / 同一外部显存采样器), 汇总成 RESULTS.md.
#
# 用法(在 study/ 目录下):
#   bash labs/module-serving-unfused/bench/run_all.sh [场景...]        # 默认 s1 s2 s3 s4
# 环境变量:
#   NANO_DIR   nano-vllm 源码目录(含 .venv), 默认 ~/nano-vllm
#   HF_MODEL   nano-vllm 用的 HF 权重目录, 默认 ~/huggingface/Qwen3-0.6B
#   OUT_DIR    结果目录, 默认 /tmp/genllm-bench-unfused
#   MS_ARGS    追加给两个 Zig 引擎的参数(如 "--policy chunked")
#   NV_ARGS    追加给 nano-vllm 的参数
#   GPU_UTIL   三边共用的 gpu_memory_utilization, 默认 0.9
#   FUSED      1(默认)= 同时跑融合版 module-serving 作参照; 0 = 只比 unfused 与 nano-vllm
#   MATCHED    1(默认)= 追加「对齐 KV 容量」场景 s3kv: nano-vllm 用 MATCHED_UTIL(默认 0.5), Zig 引擎分配同样多 KV
set -euo pipefail

HERE="$(cd "$(dirname "$0")" && pwd)"
STUDY="$(cd "$HERE/../../.." && pwd)"
NANO_DIR="${NANO_DIR:-$HOME/nano-vllm}"
HF_MODEL="${HF_MODEL:-$HOME/huggingface/Qwen3-0.6B}"
OUT_DIR="${OUT_DIR:-/tmp/genllm-bench-unfused}"
GPU_UTIL="${GPU_UTIL:-0.9}"
FUSED="${FUSED:-1}"
PY="$NANO_DIR/.venv/bin/python"
GGUF="$STUDY/weights/Qwen3-0.6B-BF16.gguf"
SCENES=("$@")
[ ${#SCENES[@]} -eq 0 ] && SCENES=(s1 s2 s3 s4)

ZIG_ENGINES=(module-serving-unfused)
[ "$FUSED" = "1" ] && ZIG_ENGINES+=(module-serving)

mkdir -p "$OUT_DIR/wl"
export LD_LIBRARY_PATH=/usr/local/cuda/lib64:${LD_LIBRARY_PATH:-}

echo "== 构建 ${ZIG_ENGINES[*]}(ReleaseFast)"
STEPS=()
for e in "${ZIG_ENGINES[@]}"; do STEPS+=("install-lab-$e"); done
(cd "$STUDY" && zig build "${STEPS[@]}" -Dcuda=true -Dnvcc=/usr/local/cuda/bin/nvcc -Dmetal=false -Doptimize=ReleaseFast)
"$PY" "$HERE/gen_workload.py" "$OUT_DIR/wl"

# run <engine> <scene> <cmd...>: 后台启动, 外部采样显存, 等结束
run() {
    local eng=$1 scene=$2
    shift 2
    echo "== $eng / $scene"
    "$@" > "$OUT_DIR/$eng-$scene.log" 2>&1 &
    local pid=$!
    "$PY" "$HERE/gpu_mon.py" $pid "$OUT_DIR/$eng-$scene.gpu.json" &
    local mon=$!
    wait $pid || { echo "!! $eng/$scene 失败, 见 $OUT_DIR/$eng-$scene.log"; tail -20 "$OUT_DIR/$eng-$scene.log"; }
    wait $mon || true
    grep -E "轮" "$OUT_DIR/$eng-$scene.log" || true
    sleep 3 # 让显存彻底释放
}

for s in "${SCENES[@]}"; do
    for e in "${ZIG_ENGINES[@]}"; do
        run "$e" "$s" "$STUDY/zig-out/bin/lab-$e" bench "$OUT_DIR/wl/$s.json" \
            --model "$GGUF" --gpu-util "$GPU_UTIL" --out "$OUT_DIR/$e-$s.json" ${MS_ARGS:-}
    done
    run nano-vllm "$s" "$PY" "$HERE/bench_nanovllm.py" "$OUT_DIR/wl/$s.json" \
        --model "$HF_MODEL" --gpu-util "$GPU_UTIL" --out "$OUT_DIR/nano-vllm-$s.json" ${NV_ARGS:-}
done

# ---- 对齐 KV 容量的显存对比(默认开; MATCHED=0 关闭) ----
# 先用 MATCHED_UTIL 跑 nano-vllm, 读出它的 KV token 数, 再让 Zig 引擎用 --kv-blocks 分配同样多的 KV.
REPORT_SCENES=("${SCENES[@]}")
if [ "${MATCHED:-1}" = "1" ]; then
    MU="${MATCHED_UTIL:-0.5}"
    ms="s3kv"
    cp "$OUT_DIR/wl/s3.json" "$OUT_DIR/wl/$ms.json"
    run nano-vllm "$ms" "$PY" "$HERE/bench_nanovllm.py" "$OUT_DIR/wl/$ms.json" \
        --model "$HF_MODEL" --gpu-util "$MU" --out "$OUT_DIR/nano-vllm-$ms.json" ${NV_ARGS:-}
    KV_TOK=$("$PY" -c "import json;print(json.load(open('$OUT_DIR/nano-vllm-$ms.json'))['kv_tokens'])")
    BS=16
    for e in "${ZIG_ENGINES[@]}"; do
        run "$e" "$ms" "$STUDY/zig-out/bin/lab-$e" bench "$OUT_DIR/wl/$ms.json" \
            --model "$GGUF" --block-size $BS --kv-blocks $((KV_TOK / BS)) \
            --out "$OUT_DIR/$e-$ms.json" ${MS_ARGS:-}
    done
    REPORT_SCENES+=("$ms")
fi

"$PY" "$HERE/report.py" "$OUT_DIR" "${REPORT_SCENES[@]}" | tee "$OUT_DIR/RESULTS.md"

常见错误

现象原因和处理
nano-vllm 报 flash-attn 空 queryprompt 长度恰为 256 的整数倍、且命中 prefix cache 时触发。workload 每轮 prompt 不同就是为了避开它。别自己改成重复 prompt。
gpu_mon.py 报找不到 pynvml装在 nano-vllm 的 venv 里：~/nano-vllm/.venv/bin/pip install pynvml。
第二个引擎报显存不够上一个进程的显存还没释放完。把 sleep 3 调大。
三个引擎的 KV 容量差很多0.9 的比例下各家扣除项不同，属正常（lab 的表里是 176736 / 176736 / 174336）。差到一倍以上说明 llmgen 的预算算错了。
llmgen 的 S3 TTFT p99 比目标高很多S3 的 256 条 prompt 共 14 万 token，prefill 要好几步。看是不是 max_num_batched_tokens 设小了。

检查点

  • RESULTS.md 里四个场景三个引擎都有数字
  • “llmgen vs 目标”一列在 0.9–1.1 之间
  • M3：S2 / S3 / S4 的吞吐和延迟全面超过 nano-vllm
