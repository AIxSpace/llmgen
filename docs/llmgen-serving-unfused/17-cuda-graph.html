阶段 4 · 执行层

CUDA Graph

decode 整步录下来，每步一次 launch。

本步目标decode 步的五百多个 kernel 录成一张 CUDA Graph，之后每步只调一次 cudaGraphLaunch。host 侧的 launch 开销从每步 2 ms 降到 0.4 ms。

原理

launch 本身的开销

第 07 步之后 host 不再等 GPU，但发射 kernel 这件事本身还要花时间：每次 cudaLaunchKernel 约 4 µs（参数打包、驱动调用）。Zig 侧每个节点还有派发、读 g_step、算 grid 大小等。

unfused 的图每层 18 个节点，一步 510 次 launch，纯 launch 开销约 2.0 ms。而此时整步的 ITL 才 3 ms 左右：GPU 干活的速度已经快到 host 发命令跟不上了。

融合版 eager 模式下，S1 全程 38 万次 launch 花了 1.5 秒；开 CUDA Graph 后变成 1338 次 cudaGraphLaunch，共 0.53 秒。host 腾出来的时间全在 cudaStreamSynchronize 里等 GPU：GPU 成了瓶颈，这才是对的。

CUDA Graph 是什么

在一条 stream 上“开始录制”之后，发射的 kernel 不执行，而是连同全部参数被记进一张图；“结束录制”得到一个可执行对象。之后 cudaGraphLaunch 一次调用就把整张图排进 stream，驱动内部不再逐个处理 kernel。

backend/cuda/cuda_context.cu（加到 llmgen 的 cuda_context.cu 末尾，文件头加 static cudaGraph_t g_capture_graph = nullptr;） lab 参考（3090 实测过）
extern "C" int cuda_graph_begin(void) {
    return (int)cudaStreamBeginCapture(g_cuda_stream, cudaStreamCaptureModeThreadLocal);
}
extern "C" void *cuda_graph_end(void) {
    CUDA_CHECK(cudaStreamEndCapture(g_cuda_stream, &g_capture_graph));
    cudaGraphExec_t exec = nullptr;
    CUDA_CHECK(cudaGraphInstantiate(&exec, g_capture_graph, 0));
    cudaGraphDestroy(g_capture_graph);
    g_capture_graph = nullptr;
    return (void *)exec;
}
extern "C" void cuda_graph_launch(void *exec) {
    CUDA_CHECK(cudaGraphLaunch((cudaGraphExec_t)exec, g_cuda_stream));
}
extern "C" void cuda_graph_destroy(void *exec) {
    if (exec) cudaGraphExecDestroy((cudaGraphExec_t)exec);
}

参数是录死的

回放时每个 kernel 的参数和录制时一字不差：指针、行数、grid 大小都是。所以一步里所有会变的东西必须满足下面两条之一：

会变的东西怎么处理哪一步准备的
token id、位置、slot、块表、上下文长度、温度、种子放在显存的元数据包里。指针不变，每步更新内容04
每个节点的输出地址活跃区间规划：同样的 (T, S) 地址恒定16
KV cache 地址每层 K / V 一整块，启动时切好不再动06
批大小 S参数里有 S，变不了。按 S 分桶，每个桶录一张图本步
上下文长度影响的 grid 大小split-K 的 grid 按 max_parts 发满，多出来的 block 读到 t0 ≥ ctx 直接返回06（kernel 设计）
cuBLAS 的临时显存固定 workspace，录制期间不许 malloc12

回头看，阶段 1 的很多设计（元数据放显存、位置查表而不是算、随机数无状态）都是为了这一步。

只录 decode

decode 步的形状只由批大小 S 决定（T = S），可以穷举。prefill 步的 T 是任意的，没法预先录，也不值得：prefill 一步的 kernel 都很重，launch 开销占比小。

分桶和 padding

桶取 1, 2, 4, 8, 16, 32, 48, …（和 nano-vllm 相同）。实际批大小 5 用桶 8，多出来的 3 行是 padding：

executor.zig · fillMeta 末尾 lab 参考（3090 实测过）
        // CUDA Graph 桶的 padding 行: ctx=0(注意力输出 0)、slot=-1(不写 KV)
        var s = entries.len;
        while (s < Sn) : (s += 1) {
            ids[t] = 0;
            pos[t] = 0;
            slots[t] = -1;
            t += 1;
            cu_q[s + 1] = @intCast(t);
            ctx[s] = 0;
            last[s] = @intCast(t - 1);
            temps[s] = 0;
            @memset((bt + s * mb)[0..mb], 0);
        }
    }

padding 行的 slot = -1，store_kv 跳过；ctx = 0，注意力输出 0；采样出来的 token 没人读。它们白算了一遍 Linear，这是分桶的代价，也是第 12 步 GEMV 阈值定在 2 的原因。

src/executor.zig 新增
const MAX_BUCKETS = 64;

// ---- 字段 ----
    enforce_eager: bool = false, // LLMGEN_EAGER=1:不录也不回放, 全部逐 kernel 发射
    buckets: [MAX_BUCKETS]usize = undefined, //            每个桶的批大小
    n_buckets: usize = 0,
    graphs: [MAX_BUCKETS]?*anyopaque = [_]?*anyopaque{null} ** MAX_BUCKETS,
    graph_out: [MAX_BUCKETS]usize = [_]usize{0} ** MAX_BUCKETS, // 每个桶回放时采样结果所在的显存地址
    n_graph_steps: usize = 0,
    n_eager_steps: usize = 0,

    fn bucketFor(self: *const Self, s: usize) ?usize {
        for (self.buckets[0..self.n_buckets], 0..) |b, i| {
            if (b >= s) return i;
        }
        return null;
    }

    /// 纯 decode 步按批大小分桶录制。桶:1, 2, 4, 8, 16, 32, 48, ... ≤ MAX_SEQS, 再补上 MAX_SEQS 本身。
    fn captureGraphs(self: *Self) !void {
        var list: std.ArrayList(usize) = .empty;
        defer list.deinit(self.allocator);
        for ([_]usize{ 1, 2, 4, 8 }) |b| if (b <= MAX_SEQS) try list.append(self.allocator, b);
        var b: usize = 16;
        while (b <= MAX_SEQS) : (b += 16) try list.append(self.allocator, b);
        if (list.items[list.items.len - 1] != MAX_SEQS) try list.append(self.allocator, MAX_SEQS);
        if (list.items.len > MAX_BUCKETS) return error.TooManyBuckets;

        // RoPE 表等只算一次的节点先算好, 不能录进图里
        try self.runPersistentOnce();

        for (list.items, 0..) |bs, i| {
            const lay = Layout.init(bs, bs, 0, self.max_blocks);
            // 预热一次:让 cuBLAS 选好算法、驱动加载好 kernel。内容无所谓:ctx = 0 / slot = -1, 不读写 KV
            self.fillMeta(lay, &.{}, bs, 0);
            self.uploadMeta(lay.total);
            self.resolveDims(@intCast(bs), @intCast(bs));
            self.bindStep(lay, bs, bs, 0, true);
            self.plan.bind(self.tok_arena, self.seq_arena, bs, bs);
            try self.runNodes();
            cuda.CudaContext.instance().sync();

            if (cuda.cuda_graph_begin() != 0) return error.GraphCaptureFailed;
            try self.runNodes(); // 这一遍 kernel 不执行, 只被记下来
            const g = cuda.cuda_graph_end() orelse return error.GraphCaptureFailed;
            self.buckets[i] = bs;
            self.graphs[i] = g;
            self.graph_out[i] = @intFromPtr(self.output_tensor.data.?);
            self.n_buckets = i + 1;
        }
    }

回放时 Zig 侧的派发代码完全不执行runNodes、dispatchKernel、各个 Impl.execute 在回放时都不会被调用。所以任何“每步要在 host 上做的事”都不能藏在 Impl 里。阶段 1–3 的 Impl 只做“读 g_step、调 C 接口”，没有副作用，满足这个要求。resolveDims 和 bindStep 在回放路径上也不调：dims 和 g_step 只在发射 kernel 时才被读。

对拍验证

回放的就是录下来的那些 kernel，输出必须和 LLMGEN_EAGER=1 逐 token 相同（greedy）。这是这一步最重要的检查：

终端 命令
LLMGEN_WORKLOAD=…/s1.json make llmgen-cuda                 # 默认: decode 回放 CUDA Graph
LLMGEN_EAGER=1 LLMGEN_WORKLOAD=…/s1.json make llmgen-cuda  # 逐 kernel 发射

如果两者不同，说明有东西在录制后变了但没放进元数据。最常见的是某个 Impl 把随步变化的标量当参数传给了 kernel。

常见错误

现象原因和处理
error.GraphCaptureFailed录制期间有不能录的操作：同步拷贝、cudaMalloc、cudaStreamSynchronize、cuBLAS 自己申请 workspace。检查 runNodes 路径上有没有残留的 sync（sync_each 和 profiler 分支在 eager 之外不该进）。
回放的输出和 eager 不同有随步变化的值被录死了。逐个检查 Impl：传给 C 接口的参数只能是 g_step 里的规模 / 指针、节点的 data、权重指针、模型常数。
回放输出恒定不变（每步同一个 token）元数据没更新到录制时的那块显存。Layout.init(Tn, Sn, 0, …) 回放时的参数必须和录制时相同，否则各段偏移不同。
带温度采样时每步抽到同样的噪声seed 没更新。它在元数据包头 8 字节，fillMeta 每步递增，随 uploadMeta 上传。
第一步 decode 很慢正常，第一次 cudaGraphLaunch 有一次性的初始化。压测前先预热（第 21 步）。
LLMGEN_PROFILE=1 下没有 graph 步设计如此：profile 要逐算子同步，只能 eager。

检查点

  • greedy 输出：默认和 LLMGEN_EAGER=1 逐 token 相同
  • n_graph_steps ≈ 生成的 token 数，n_eager_steps ≈ prefill 的次数
  • M2：S1 的吞吐、ITL、TTFT 接近目标
  • 阶段 4 结束：把数字填进总览页的汇总表
