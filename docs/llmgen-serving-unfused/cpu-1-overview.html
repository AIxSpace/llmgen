CPU 支线

CPU：一套执行层两个后端

主线每做一步，CPU 都还能跑，并且和 CUDA 逐 token 相同。

本步目标弄清为什么同一套执行层能同时驱动 CPU 和 CUDA，以及主线每一步 CPU 要跟着做什么。读完这一页，你手里有一张对照表：做主线第 N 步时，去 CPU 支线的哪一节。

原理

执行层是设备无关的

主线阶段 1 搭起来的东西：图、每步的元数据包（StepState）、slot 寻址的分页 KV、活跃区间激活规划、连续批处理。这些都不依赖 GPU。它们只规定了“数据放在哪、每个算子读什么”，没规定算子怎么算。

所以 CPU 后端要做的只是：每个算子提供一个 CPU 特化，读同样的输入、同样的元数据，写同样布局的输出。目标 lab 就是这样做的：backend/cpu/ 和 backend/cuda/ 文件一一对应，执行层一行不分叉。

CPU 和 CUDA 只在三处不同

CUDACPU
内存池显存，host 不能解引用普通内存，host 直接读写
元数据写进 pinned 缓冲 → 异步 H2D直接写进 activation 池里那块缓冲，不用拷贝
取结果异步 D2H 4·S 字节 + 同步 stream直接读输出节点
同步cudaStreamSynchronize算子本来就是同步执行的，没有这回事
CUDA Graphdecode 步回放没有，恒 eager
split-K scratch、采样 scratch从 activation 池切不需要（CPU 算子不用）

lab 把这些差别收在三个小函数里，其余代码不知道自己跑在哪种设备上：

executor.zig：设备相关的动作全收在这三个小函数里 lab 参考（3090 实测过）
    fn uploadMeta(self: *Executor, bytes: usize) void {
        if (comptime opts.have_cuda) {
            if (self.device == .CUDA) cu.cuda_h2d_async(self.devAt(0), self.meta_host.?, bytes);
        }
    }

    /// 等本设备上已派发的工作做完(CUDA: 同步 stream; Metal: 提交已编码的命令并等待; CPU: 同步执行, 无事可做).
    fn syncDevice(self: *Executor) void {
        switch (self.device) {
            .CUDA => if (comptime opts.have_cuda) cu.cuda_sync(),
            .METAL => if (comptime opts.have_metal) metal.flush(),
            else => {},
        }
    }

    /// 取回本步 S 个采样 token(CUDA: D2H 到 pinned; CPU / Metal: 直接读输出节点).
    fn fetchOut(self: *Executor, out_ptr: usize, n_seq: usize) []const i32 {
        if (comptime opts.have_cuda) {
            if (self.device == .CUDA) {
                cu.cuda_d2h_async(self.out_host.?, @ptrFromInt(out_ptr), n_seq * 4);
                cu.cuda_sync();
                return self.out_host.?[0..n_seq];
            }
        }
        self.syncDevice();
        return @as([*]const i32, @ptrFromInt(out_ptr))[0..n_seq];
    }

主线各步给出的 llmgen 代码已经按这个思路写了：allocMeta 里 CPU 的 meta_host 直接指向池；uploadMeta、fetchOut、逐算子同步都带着 device_type == .CUDA 的判断；enforce_eager 在非 CUDA 时恒为真。所以执行层这边 CPU 几乎不用额外写代码（细节在 C5）。要写的是算子。

数值：CPU 和 CUDA 逐点对齐

lab 的 CPU 算子和 .cu 遵守同一条规则：在 f32 里算，每个 bf16 张量边界就近舍入一次，舍入点的位置也相同（比如 RMSNorm 的 round_bf(x·rstd)·w）。结果是同一个 prompt 的 greedy 输出，CPU 和 CUDA 64 个 token 逐个相同 lab CPU 实测。

这给了你一个很强的验证手段：CPU 版是 CUDA 版的活参考。CPU 算子都是几十行的朴素循环，容易看对；CUDA kernel 改出问题时，用 CPU 跑同一个 prompt，两边一比就知道是不是 kernel 的锅。

改动：选设备

纯 CPU 构建（不带 -Dcuda=true）时设备列表里只有 CPU，什么都不用改。带 CUDA 构建时，调度器会优先把层分给 GPU；想在同一个二进制里跑 CPU，就只把 CPU 这一台设备交给它：

每一步怎么验证

终端 命令
# mac 或没有 GPU 的机器:纯 CPU 构建
zig build run -Doptimize=ReleaseFast

# 3090 上:同一个二进制, 用 --device 选(第 21 步之前用环境变量 LLMGEN_DEVICE=cpu)
./zig-out/bin/llminfer chat "中国的首都是哪里？" 64 --device cpu
./zig-out/bin/llminfer chat "中国的首都是哪里？" 64 --device cuda
  • CPU 自己跑通：输出通顺，和上一步的 CPU 输出逐 token 相同（或在主线说明的“允许分叉”的步骤里前 20 个相同）。
  • CPU 对 CUDA：同一个 prompt、temperature = 0，两边的 token id 逐个相同。从第 12 步起这应该严格成立；之前的步骤里 CUDA 还有旧 kernel，舍入点不同，允许近似并列处分叉。
mac 上也能做大部分步骤CPU 后端不依赖 CUDA。主线里执行层的改动（04、08、16、18–21）可以先在 mac 上用纯 CPU 构建跑通、对拍，再上 3090 验证 CUDA。

对 llmgen 的预期

CPU 支线不是为了让 CPU 跑得多快，是为了一直能跑。但做完之后速度也会差出两个数量级：

llmgen 早期的 CPU 日志里，8 次前向（1 次 prefill + 7 次 decode）用了 139 秒 llmgen 早期 CPU 日志，其中 99.3% 在 Linear（单线程、逐元素 elemF32）。lab 的 CPU 后端在同类机器上是 21 tok/s。差别来自三处：多线程、SIMD、bf16 直接读（不做逐元素的 dtype 分支），都在 C2 和 C4。

那份早期日志不是当前起点（commit 91fac54）量的，只说明量级。当前起点的 CPU 数字请自己量一次填在下面。

常见错误

现象原因和处理
带 CUDA 构建时 LLMGEN_DEVICE=cpu 仍然跑在 GPU 上调度器收到的设备列表里还有 CUDA。只传 CPU 那一项。
CPU 上段错误，栈在某个 cuda_* 函数有 Impl 或执行层代码没判断设备就调了 CUDA 接口。按“三处不同”那张表逐项查。
CPU 和 CUDA 的输出从第一个 token 就不同不是舍入问题。多半是某个 CPU 算子还是旧布局（head-major）或旧接口。
