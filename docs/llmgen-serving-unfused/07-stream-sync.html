阶段 1 · 去掉主机开销

一条 stream，一步一同步

host 一口气发完整步的 kernel，只等一次。

本步目标所有 kernel 排进同一条 CUDA stream，host 一口气把整步的 kernel 发完，只在最后取结果时等一次。同步次数从每步 500 多次降到 1 次。

原理

launch 是异步的

kernel<<<…>>>(…) 只是把一个任务放进队列就返回，GPU 在后台按顺序执行。host 可以连着发几百个 kernel 而不等任何一个。只有 host 要读结果时才需要等。

一步前向里，host 真正需要读的只有最后的 logits（第 09 步之后是一个 token id）。中间那五百个 kernel 的输出都留在显存里给下一个 kernel 用，host 根本不看。

起点却在每个 kernel 后面都等：

每算子同步
发 A等 A发 B等 B发 C等 C…
GPU
·A·B·C
一步一同步
发 A发 B发 C…发 Z等一次
GPU
·ABC…Z
上：host 和 GPU 轮流干活，互相等。下：host 发命令和 GPU 执行重叠，GPU 不空转。

每次同步的代价有两部分：系统调用和线程唤醒的固定开销；以及 GPU 做完一个 kernel 后空转，等 host 醒来发下一个。decode 的 kernel 大多只跑几微秒，空转的时间比干活的时间还长。

为什么要一条独立的 stream

stream 是一条 FIFO 队列，同一条 stream 里的操作严格按提交顺序执行，这就保证了 kernel B 一定在 kernel A 之后跑，不需要 host 来排。

现在所有 kernel 都在默认 stream 上。默认 stream 有个特殊语义：它上面的每个操作都会和其它（阻塞型）stream 隐式同步。换成一条用 cudaStreamNonBlocking 创建的独立 stream 之后：

  • 可以用 cudaStreamSynchronize(stream) 只等这一条，比 cudaDeviceSynchronize 轻；
  • cuBLAS 可以绑到同一条 stream 上，和自写 kernel 排在一起；
  • 第 17 步的 CUDA Graph 录制是按 stream 录的（cudaStreamBeginCapture），默认 stream 不能录。
backend/cuda/cuda_context.cu lab 参考（3090 实测过）
cudaStream_t g_cuda_stream = nullptr;
cublasHandle_t g_cublas = nullptr;
static void *g_cublas_ws = nullptr;
static cudaGraph_t g_capture_graph = nullptr;

extern "C" int cuda_init(size_t ws_bytes) {
    if (g_cuda_stream) return 0;
    int count = 0;
    if (cudaGetDeviceCount(&count) != cudaSuccess || count <= 0) {
        fprintf(stderr, "[serve] no CUDA device\n");
        return 1;
    }
    CUDA_CHECK(cudaSetDevice(0));
    CUDA_CHECK(cudaStreamCreateWithFlags(&g_cuda_stream, cudaStreamNonBlocking));
    if (cublasCreate(&g_cublas) != CUBLAS_STATUS_SUCCESS) {
        fprintf(stderr, "[serve] cublasCreate failed\n");
        return 2;
    }
    cublasSetStream(g_cublas, g_cuda_stream);
    // 固定 workspace: CUDA Graph 录制期间 cuBLAS 不能自己申请显存
    if (ws_bytes > 0) {
        CUDA_CHECK(cudaMalloc(&g_cublas_ws, ws_bytes));
        cublasSetWorkspace(g_cublas, g_cublas_ws, ws_bytes);
    }
    cublasSetMathMode(g_cublas, CUBLAS_DEFAULT_MATH);
    return 0;
}

为什么这一步排在第 06 步之后

去掉逐算子同步之后，一步之内所有操作必须能排进同一条队列。前几步做的事正是把不能排队的东西清掉：

原来热路径上有问题哪一步清掉的
同步 cudaMemcpy（写 KV、块表）走默认 stream。换成非阻塞 stream 后，它不会等我们的 kernel，会读到还没算完的数据06
cudaFree（块表）kernel 还在队列里没跑，它要读的显存就被释放了06
CPU 上的 embeddinghost 要参与计算，就得先等 GPU03
RoPE 起点写在 op_params没问题，但 CUDA Graph 回放时改不了05

现在一步里只有：一次元数据上传、五百个 kernel、一次 logits 回拷。全都能排队。

1建 stream

2老 kernel 的发射点加上 stream

从 lab 搬来的 kernel（embedding、rope、attention）本来就写了 g_cuda_stream。llmgen 自己的几个老 kernel 还没有：arithmetic.cu（add / mul）、activation.cu（silu）、norm_warp.cu。

每个老 kernel 的发射点：第三个参数是动态 shared memory 字节数（0），第四个是 stream 改动对比
        add_kernel<<<blocks, threads>>>(static_cast<const __nv_bfloat16*>(in1), ...);        add_kernel<<<blocks, threads, 0, g_cuda_stream>>>(static_cast<const __nv_bfloat16*>(in1), ...);
终端 命令
# 还排在默认 stream 上的发射点。输出应该只剩已经不用的文件(shape.cu / softmax.cu / linear_naive.cu ...)

漏一个都不行漏掉的 kernel 会跑在默认 stream 上，和我们的 stream 没有先后关系：它可能在前一个 kernel 写完之前就开始读。症状是结果偶尔错、每次错得不一样。改完务必跑一遍上面的 grep。

pageable 和 pinned 的区别cudaMemcpyAsync 从普通（pageable）host 内存拷到显存时，驱动要先把数据搬到内部的 pinned 暂存区，这一步可能在后台线程里做，调用返回时 host 缓冲还在被读。所以异步 H2D 的 host 缓冲必须是 pinned 的，并且在这一步结束前不能改。元数据缓冲是 cudaMallocHost 分的，每步 fillMeta 之前上一步已经同步过，满足条件。
cuda_h2d / cuda_d2h 用在权重加载和单测里，host 缓冲是普通内存，所以保留“拷完再返回”的语义：排进 stream，再等 stream。

CPU 同步

这一步 CPU 后端要做的事不用动。CPU 算子本来就是同步执行的，没有 stream。executorTensor 里的同步带着设备判断，CPU 上不会走到。

对 llmgen 的预期

lab 的消融（--sync-each）：融合版每层 9 个节点、每步 252 次同步，去掉后 S1 快 1.49 倍，ITL 省 1.12 ms，折合每次同步 4.4 µs。S4 快 1.60 倍。

llmgen 现在每步约 508 个 kernel（每层 18 个，加上 embedding、final_norm、lm_head 和拷贝），同步次数是融合版的两倍。按每次 4.4 µs 算，预期 ITL 省 2.2 ms 左右 推算。

省多少倍取决于此时的 ITL：如果第 06 步之后 ITL 已经降到十几毫秒，这一步是 15–20% 的提升；等阶段 3 把 kernel 换完、ITL 降到 3 ms 时再用 LLMGEN_SYNC_EACH=1 回头量，差距会接近 lab 的 1.5 倍。固定开销不变，其余部分越快，它占的比例越大。
