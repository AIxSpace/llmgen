连续批处理（Continuous Batching）详解

从调度、抢占、拆趟执行，到变长 token 拼接和元数据布局。代码路径都相对于项目根目录。

01整体流程

每一步（每生成一个 token）都会完整走一遍下面这条链路，src/runner/engine.zig 的 step 负责串起来：

schedule()batching.zig · 选出本步的 Entry 列表
→
execute()executor.zig · 超出容量就拆趟
→
forward()fillMeta → 拷到显存 → 跑计算图
→
emits() 过滤engine.zig · 只保留产出 token 的条目
→
postprocess()追加 token，结束的移出并释放 block

核心数据结构 Entry（batching.zig:93）描述"这一步要对哪条序列的哪一段 token 做前向"：

pub const Entry = struct {
    seq: *Sequence,
    q_start: usize,   // 本步从序列的第几个 token 开始算
    q_len: usize,     // 本步算多少个 token

    // 算到了序列当前最后一个 token → 本步会产出一个新 token
    // decode 永远为真；prefill 最后一块为真；chunked prefill 的中间块为 false
    pub fn emits(self: Entry) bool {
        return (self.q_start + self.q_len) == self.seq.len();
    }
};

02Continuous Batching

src/runner/batching.zig 实现的就是 continuous batching（迭代级调度），带两种调度策略、基于 block 的 KV 分配和抢占，结构上和 nano-vllm / vLLM 的调度器基本一致。

和 static batching 的区别

Static batchingContinuous batching
组批时机凑齐一批再开跑每一步都重新组批
序列结束等全批最长的那条跑完，先结束的位置空转结束马上移出，资源立刻释放
新请求加入等下一批下一步就能插进来

代码里的对应位置

  • 每步重新调度：schedule()（batching.zig:145）每次先 clearRetainingCapacity()，再按 waiting / running 的当前状态重新组批。
  • 结束就离场：postprocess()（batching.zig:316-325）碰到 EOS 或到达 max_tokens，立刻 deallocate 释放 block，并从 running 移除。
  • 新请求随时进场：add() 只是追加到 waiting；下一次 schedule() 只要预算和 block 够，就拉进 running。

时间线示例（prefill_first）

stepwaiting本步调度说明
1[A, B]prefill A, B两条一起 prefill
2[]decode A, B
3[C]prefill CC 到了，prefill 优先，A、B 这步暂停
4[]decode A, B, CC 直接并入正在跑的批
5[]decode A, B, CA 碰到 EOS，移出并释放 block
6[]decode B, CA 的位置马上让出来

两种调度策略

prefill_first（:155）chunked（:220）
对应实现nano-vllm、vLLM V0 默认Sarathi-Serve、vLLM V1
一步里的内容要么全是 prefill，要么全是 decodeprefill 分块和 decode 混在同一步
prefill 长度整段 prompt 一次算完每步最多 chunk_tokens
优点实现简单；纯 decode 步能用 CUDA Graphdecode 不会被长 prefill 卡住，ITL 更平稳
缺点新请求一来 decode 就停一步（decode 饥饿）混合步一般用不上 CUDA Graph

chunked 里先处理 running（decode 和没算完的 prefill），剩下的预算再从 waiting 接新请求：老序列优先。

配套机制

  • Paged KV（block_table + BlockManager）：KV 按块按需分配，不用给每条序列预留 max_model_len。
  • 抢占（preempt）：block 不够时把后来的序列踢回 waiting 队首，之后重新 prefill（recompute 方式）。
  • num_computed_tokens + emits()：记录每条序列算到哪里，chunk 中间块不产出 token。

和完整版 vLLM 相比还缺

  • Prefix caching（相同前缀共享 KV block）
  • Swap 方式抢占（把 KV 换到 CPU，而不是丢掉重算）
  • 优先级 / 公平调度（现在是纯 FIFO）

另外，chunked 从 waiting 接新请求时 ensure 失败就直接 break，不会为新请求抢占老请求。这是合理的选择，否则容易来回抖动。

03抢占逻辑

为什么 decode 会缺块

decode 时 seq.len() 已经包含上一步刚采样出的 token，但它的 KV 还没写进 cache。这步 forward 要把它写进去，所以要能装下 seq.len() 个 token。长度一旦跨过块边界（比如 block_size=16，长度从 16 变成 17），就要再申请一块。

canEnsure(seq, n)（block.zig:64）只检查不分配：已有块够用，或者缺的块数 ≤ 空闲块数，返回 true。

循环逻辑（batching.zig:195）

while (!canEnsure(seq, seq.len())) {          // 序列 i 缺块
    if (running.len - 1 > i) {                // i 后面还有别的序列
        preempt(running.pop().?);             // 踢掉队尾，释放它的块，再检查一次
    } else {                                  // i 自己就是队尾
        _ = running.orderedRemove(i);
        preempt(seq);                         // 把自己也踢掉
        ok = false;
        break;                                // 本轮 decode 调度结束
    }
}

规则：先来的优先保住，后来的先被牺牲。running 按进入顺序排列，下标越小越早。ok 标志用于跳出外层 while：内层 break 只能跳出抢占循环。

例子：running = [A, B, C, D]，空闲块为 0

步骤i情况动作runningwaiting
10A 不用新块调度 A[A,B,C,D][]
21B 缺 1 块pop D，释放 D 的块[A,B,C][D]
31块够了ensure 分配，调度 B[A,B,C][D]
42C 缺块，自己是队尾踢掉 C，break[A,B][C,D]

细节

  • waiting 顺序不乱：preempt 用 insert(0, seq) 插到队首。从队尾往前踢，D 先进、C 后插到它前面，结果是 [C, D]。
  • 被抢占就要重算：deallocate 把 num_computed_tokens 清 0，KV 全丢，下轮整段重新 prefill（prompt + 已生成的 token）。
  • 先 canEnsure 再 ensure：确认够了才真正拿块，不会出现分了一半又失败的状态。
  • scheduleChunked 里有一段相同的抢占逻辑，区别只是检查 upto（本轮 chunk 算到的位置）而不是 seq.len()。

04execute 拆趟

调度出来的一批 token 总数可能超过执行器单趟能放下的上限 limit.max_tokens（激活区、元数据区都按这个上限预分配）。超出时，execute（executor.zig:948）把这一批拆成几趟依次跑，结果按原 entries 顺序拼回去。

execute(entries)
 ├─ 序列条数 > max_seqs        → 报错（序列区放不下，拆趟也没用）
 ├─ 总 token 数 ≤ max_tokens   → 一趟 forward 直接返回（常见情况）
 └─ 总 token 数 > max_tokens   → 拆成多趟

三个辅助数组

变量含义
pass_out最终结果，长度 = entries.len，第 i 个是 entries[i] 的采样 token
pass_group当前这一趟要跑的"片段"，每个片段也是 Entry，只覆盖原条目的一部分
pass_owner和 pass_group 一一对应，记录每个片段来自 entries 的第几条

切分循环

var room = max_tokens;                         // 当前这趟还能装多少 token
for (entries, 0..) |e, idx| {
    var qs = e.q_start;
    var left = e.q_len;
    while (left > 0) {
        const take = @min(left, room);         // 能装多少装多少
        pass_group.append({ e.seq, qs, take });
        pass_owner.append(idx);
        qs += take; left -= take; room -= take;
        if (room == 0) {                       // 装满了，立刻跑一趟
            flushPass(entries);
            room = max_tokens;
        }
    }
}
flushPass(entries);                            // 最后一趟没装满也要跑

flushPass：跑一趟并回收结果（executor.zig:989）

const toks = forward(pass_group.items);        // 每个片段返回一个采样 token
for (pass_group, pass_owner, toks) |piece, owner, tk| {
    const e = entries[owner];
    if (piece.q_start + piece.q_len == e.q_start + e.q_len)  // 是该条目的最后一段
        pass_out[owner] = tk;
}

只有原条目最后一段的采样结果有意义；中间片段的末尾不是条目末尾，采出来的 token 直接丢掉。

例子：max_tokens = 8

idx条目q_startq_len
0A：prefill，prompt 长 10010
1B：decode301
2C：decode151
  • 第 1 趟：A[0..8)，满了就 flush。片段末尾 8 ≠ 10，结果丢弃。这一趟的作用是把 A 前 8 个 token 的 KV 写进 cache。
  • 第 2 趟：A[8..10)、B、C。A 末尾 10 = 10，写入 pass_out[0]；B、C 分别写入 pass_out[1]、pass_out[2]。

为什么拆开跑结果还是对的

  • KV Cache 起衔接作用：第 2 趟算 A[8..10) 时，attention 从 cache 读前 8 个位置，等同于一次算完。原理和 chunked prefill 相同。
  • 同一序列的片段不会在同一趟：只有 room == 0 才切断序列，而 room 归零会立刻 flush，保证先写 KV 后读 KV。
  • 非 emit 条目会被过滤：pass_out 里也有值，但 engine.zig:135 只取 e.emits() 为真的条目。

05拆趟的好处与代价

核心好处：把"一步调度多少 token"（调度器的决定）和"一趟 forward 能装多少 token"（执行器的显存限制）解耦。

好处

  1. 显存上限可预测：激活区（tok_arena）、元数据区（meta）启动时按 max_tokens 一次性切好，运行时不扩。拆趟保证一趟永远不超，不会越界也不会 OOM。
  2. 调度器不用关心执行器的内存细节：调度器按自己的 max_batched_tokens_num（默认 16384）和 KV block 决定跑谁，执行器保证都能跑完，返回格式不变。
  3. 长 prompt 也能跑：prefill_first 下 prompt 是整段 prefill，比 max_tokens 长时，拆趟相当于在执行层自动做了 chunked prefill。
  4. 激活显存可以设小一点：激活区 ≈ max_tokens × 每 token 字节数，设小之后省下的显存留给 KV Cache，能同时跑的序列更多、抢占更少。

代价

代价原因
权重要多读几遍每趟都要把全部层的权重读一遍，拆成 N 趟就读 N 次
中间片段的采样白算非最后一段的结果被丢弃（lm_head 只算最后一行，开销不大）
这一步的延迟变长N 趟串行，同一步里的 decode 序列要等所有趟跑完，ITL 出现尖峰
用不上 CUDA Graph拆出来的批一般含 prefill 片段，走 eager 路径

拆趟是兜底的安全网，不是常规路径。最理想的配置是让调度器的 token 预算（max_batched_tokens_num 或 chunk_tokens）不超过执行器的 max_tokens，大多数步都走一趟的快路径。

06max_tokens 怎么定

src/graph/scheduler.zig:32 的 max_tokens: usize = 1024 只是结构体默认值。实际生效的值来自 llmgen.zig:74 传进来的 cli_opts.maxTokens()（src/cli.zig:58）：

pub fn maxTokens(self: Options) usize {
    const pass = self.pass_tokens orelse (if (opts.have_cuda) @as(usize, 8192) else 2048);
    return @max(pass, self.max_num_seqs);
}
  • 命令行 --pass-tokens <n> 指定了就用 n
  • 否则 CUDA 构建默认 8192，CPU 构建默认 2048
  • 最后和 max_num_seqs（默认 256）取较大值

决定因素

因素说明
下限：一步 decode 必须一趟装下S 条序列 decode 就是 S 个 token。max_tokens < max_num_seqs 会导致 decode 也拆趟、CUDA Graph 失效，所以有 @max
上限：和 KV Cache 抢显存KV 预算 = 总显存 × 利用率 − 已用 − 权重 − 激活 − 预留（scheduler.zig:380 之后）。激活随 max_tokens 线性增长，挤掉的是 KV block
收益：把 GPU 喂饱T 太小时 prefill 访存受限；增大到几百到几千后进入计算受限，再大吞吐基本不涨
CPU 为什么更小CPU 几百个 token 就算满了，设大只会拉长单步延迟；CPU 的 KV 固定 HOST_KV_BLOCKS = 512 块，不和激活抢

业界参考

框架参数常见默认值
nano-vllmmax_num_batched_tokens16384
vLLMmax_num_batched_tokens随版本和场景变化，chunked prefill 下常见 2048～8192，离线吞吐场景更大
本项目--pass-tokensCUDA 8192 / CPU 2048

偏小有利于降低 decode 延迟抖动（ITL），偏大有利于提高 prefill 吞吐、降低首 token 延迟（TTFT）。

怎么调

  1. 跑一次，看启动日志 [executor] 激活 token 区 xx MB (yyy B/token)（executor.zig:739）和 KV block 数
  2. 用 bench workload 分别试 --pass-tokens 2048 / 4096 / 8192 / 16384，对比吞吐、TTFT、num_preemptions
  3. 选吞吐不再明显上升、KV 仍够用（抢占不多）的那个点

07变长 token 维度

不同序列本步的 token 数不一样（prefill 几千个，decode 1 个）。这里不用 padding 对齐，而是把所有 token 首尾相接拼成一维（packed / varlen batch），再附带一份元数据说明边界和位置。

传统:    [batch, max_len, hidden]，短的补 0  → 浪费大量计算
这里:    [A0 A1 A2 | B5 | C4 C5]  → [T, hidden]，T = 6，S = 3，没有 batch 维

动态维度 DYN / DYN_S

计算图启动时只建一次，但每步 T、S 都在变。src/module/base.zig:11-12 定义了两个占位符：

pub const DYN: i64 = -1;   // 本步 token 总数 T
pub const DYN_S: i64 = -2; // 本步序列数 S

每步 forward 前 resolveDims（executor.zig:930，调用在 :571）把它们替换成真实值并重算 stride。

各算子如何处理

算子读的元数据做法
embedding / Linear / RMSNorm / MLP无逐 token 独立，[T, hidden] @ W 就是普通矩阵乘，不关心序列边界
RoPEpos第 t 行用 pos[t] 查 cos/sin，而不是行号 t
store_kvslots第 t 行的 K/V 写到 slots[t]，-1 跳过
attentioncu_q ctx block_tables按序列循环，只读本序列的行和本序列的 KV 块，天然隔离
gather_lastlast从 [T, hidden] 挑出每条序列最后一行 → [S, hidden]
sampletemps seed[S, vocab] 每行按各自温度采样

attention 的因果公式

CPU attend（backend/cpu/attention.zig:64）对序列 s 的段内第 j 个 query：

n_keys = ctx - q_len + j + 1;   // attention.zig:84，只看位置 0..自己

一个公式覆盖三种情况：

序列ctxq_len每个 query 看到的 key 数
A（完整 prefill）331, 2, 3（标准因果三角）
B（decode）616（看全部历史）
C（chunk 后半段）625, 6（4 个历史 + 段内因果）

store_kv 在 attend 之前执行（attention.zig:133），所以本步新 token 的 KV 已经在 cache 里。因为 cu_q 只给本序列的行、block_table 只指向本序列的块，不需要构造 [T, T] 的 mask。

gather_last：T → S

位于 final_norm 之后、lm_head 之前（models/qwen3.zig:324, 330）。lm_head 输出 151936 维，只让每条序列的最后一行过 lm_head，能省掉绝大部分计算。

CUDA Graph 下的 padding

纯 decode 步会把 S 向上取到桶大小（1、2、4、8、16、32、48…）。多出来的行填成无害值：slots = -1（不写 KV）、ctx = 0（attention 输出 0），采样结果由 fetchOutAt(..., n_seq) 截掉。这是整个流程里唯一用到 padding 的地方。

一句话：token 维靠"拼接 + 前缀和"解决，序列维靠 gather_last 收缩，边界全部写在元数据里，只有 RoPE、attention 等和位置相关的算子去读它。这和 vLLM 的 cu_seqlens / slot_mapping / block_tables、FlashAttention 的 varlen 接口是同一套思路。

08fillMeta 详解

fillMeta（executor.zig:764）做了两层"拼成一维"：

  1. token 层：所有 entry 的 token 首尾相接排成 T 行，靠游标 t 实现
  2. 内存层：十来个元数据数组按 Layout 的偏移塞进同一块连续缓冲 meta_host，一次拷到显存

内存层：Layout

Layout.init（executor.zig:153）不分配内存，只用一个从 8 开始累加的 offset 算出每个数组的起始字节：

seed8B
ids4·T
pos4·T
slots4·T
cu_q4·(S+1)
ctx4·S
last4·S
temps4·S
tile_seq4·tiles
tile_q04·tiles
bt4·S·max_blocks
逐 token 逐序列 prefill tile 块表

fillMeta 开头用 i32At(layout.xxx) / f32At（executor.zig:747-752）拿各段指针，只是把 meta_host + 偏移 强转成对应类型，不拷贝也不分配。

为什么挤进同一块缓冲

  • uploadMeta（:757）只需一次 cuda_h2d_async，而不是十次
  • kernel 端地址是 devAt(偏移) = meta_dev + 偏移（:753），和 host 端一一对应
  • (T, S, tiles) 相同时偏移完全相同、地址固定，CUDA Graph 回放时往同样位置写新值即可

① 写 seed

self.step_seed +%= 0x9E3779B97F4A7C15;   // 每步加一个黄金比例常数，+%= 允许回绕
std.mem.writeInt(u64, self.meta_host[0..8], self.step_seed, .little);

采样 kernel 从显存读种子，所以 CUDA Graph 回放时每步的随机数也不同。

② 主循环：拼接 token（核心）

var t: usize = 0;        // ★ 全局游标：下一个 token 写到第几行
var tile: usize = 0;
cu_q[0] = 0;

for (entries, 0..) |e, s| {
    const seq = e.seq;

    // 把这条序列本步的 q_len 个 token 依次追加到第 t 行
    for (0..e.q_len) |j| {
        const p = e.q_start + j;                         // 在自己序列里的位置
        ids[t]   = seq.all_token_ids.items[p];
        pos[t]   = @intCast(p);
        slots[t] = seq.slotOf(p, self.limit.block_size);
        t += 1;                                          // ★ 游标前进，从不清零
    }

    // 记录这条序列的边界和属性
    cu_q[s + 1] = @intCast(t);                    // 序列 s 占 [cu_q[s], cu_q[s+1]) 行
    ctx[s]      = @intCast(e.q_start + e.q_len);  // 算完本步 KV 里共有多少 token
    last[s]     = @intCast(t - 1);                // 最后一行的行号
    temps[s]    = seq.params.temperature;

    // 块表拷进第 s 行，不足 max_blocks 补 0
    const row = bt + s * mb;
    @memcpy(row[0..nb], seq.block_table.items);
    @memset(row[nb..mb], 0);

    // prefill：query 按 pf_tile(64) 切块
    if (n_tiles > 0) {
        var q0: usize = 0;
        while (q0 < e.q_len) : (q0 += self.pf_tile) {
            tseq[tile] = @intCast(s);
            tq0[tile]  = @intCast(q0);
            tile += 1;
        }
    }
}

拼成一维的关键就是游标 t：它在整个外层循环中一直累加。序列 0 写在第 0 ~ q_len₀−1 行，序列 1 紧接着写，以此类推。每条序列写完时 t 的值就是下一条的起点，存进 cu_q[s+1]。所以 cu_q 就是 q_len 的前缀和，任何 kernel 都能据此把一维数组拆回各条序列。

字段下标存的是说明
t—一维数组里的行号所有序列共享，0 到 T−1
p—在自己序列内的位置每条序列各自从 q_start 开始
pos[t]行号p行号和位置脱钩，RoPE 必须用它
ids[t]行号all_token_ids[p]decode 时 p = len−1，即上步采样、本步作为输入的 token
ctx[s]序列号q_start + q_lenchunk 中间块的 ctx 小于 seq.len()
last[s]序列号t − 1每条都填，是否有效由 engine 用 emits() 判断

③ padding 行（只有 CUDA Graph decode 才走到）

var s = entries.len;
while (s < Sn) : (s += 1) {     // Sn 是桶大小
    ids[t]   = 0;
    pos[t]   = 0;
    slots[t] = -1;              // store_kv 跳过
    t += 1;                     // 游标继续往后走
    cu_q[s + 1] = @intCast(t);
    ctx[s]   = 0;               // attend 里 ctx < q_len → 输出 0
    last[s]  = @intCast(t - 1);
    temps[s] = 0;
    @memset((bt + s * mb)[0..mb], 0);
}

padding 按同样格式拼在末尾，让一维数组长度刚好等于桶大小、和录图时形状一致。非 decode 步 Sn == entries.len，这段不执行。

④ 之后

forward 调用 uploadMeta(layout.total) 一次性拷到显存，再由 bindStep（:826）把 devAt(layout.xxx) 地址写进全局 g_step，各 kernel 从那里读。bindStep 还把 input_tensor.data 直接指向 ids 段，embedding 就从这里读 token id。

用例子验证 attention 的隔离

C 的段是 cu_q[2]..cu_q[3] = 第 4、5 行，ctx = 6，q_len = 2：第 4 行看 6−2+0+1 = 5 个 key（位置 0~4），第 5 行看 6 个（位置 0~5）。这些 key 通过 bt 第 2 行的 [0, 3] 去块 0 和块 3 读取，A、B 的 KV 完全不会碰到。

  • 拼接：游标 t 在所有序列间连续递增，token 依次追加
  • 能拆回去：cu_q 是前缀和记录每段边界，last 记录每段末行
  • 位置和行号分离：pos、slots 用序列内位置 p，不是行号 t
  • 一块缓冲：Layout 把所有数组按偏移排进 meta_host，一次拷到显存，地址固定，CUDA Graph 可复用
