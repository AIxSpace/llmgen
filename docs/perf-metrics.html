给 llmgen 加上性能指标：从一个计时器到完整的性能报告

按"先能测，再测准，再解释"的顺序，一步步把常见的推理性能指标加进 src。每一步都写清楚改哪个文件、改哪个函数、改动前后长什么样，以及调用方要跟着改什么。

第 0–4 章只涉及 executor.zig 和 profiler/ 目录；第 5–7 章开始算硬件效率；第 8 章面向还在开发中的 runner/ 连续批处理路径；第 9 章把结果变成可对比的报告。

00测量基础入门

这一章不改代码。先搞清楚"怎么测才算数"：性能数字最怕的不是慢，而是测错了却不知道。

generate 的调用链

llmgen.run()→ Executor.generate()→ prefill(prompt) → forward()→ 循环: sample() → tokenizer.decode + print → decodeStep() → forward()
forward()→ resolveDims→ 持久节点(只算一次)→ step_nodes 逐个→ executorTensor()→ allocateOutput → dispatchKernel → (CUDA) sync

改动前已有的基础设施

  • generate() 里有一个 std.time.Timer，叫 total_timer，用来算总耗时。
  • executorTensor() 在 profile 开启时为每个算子计时，交给 OpProfiler.record(op, device, ns)。
  • OpProfiler 由环境变量 LLMGEN_PROFILE 开启，关闭时连 Timer 都不启动。打印时把算子以外的时间归到"(其它)"。
  • CUDA 设备上每个算子执行完都会调用 CudaContext.sync()。

五条测量原则

  1. 用单调时钟。std.time.Timer 基于单调时钟，三个方法的区别见下面的示意。
  2. 用 ReleaseFast 测性能。Debug 构建带安全检查、不做优化，数字可能慢 10 倍以上，只能用来验证埋点逻辑。
  3. 区分冷启动和稳态。第一次 forward() 会计算持久节点（persistent_computed），还有 CUDA 上下文初始化、kernel 首次加载、页缺失等开销。
  4. GPU 计时必须同步。kernel 发射是异步的。计时区间里没有 sync 的话，量到的只是"提交"的时间。
  5. 别让测量污染结果。generate() 里每个 token 都会 tokenizer.decode 再 std.debug.print（stderr 无缓冲），这部分会被算进 TPOT，第 4 章会把它单独拆出来。
检查点
  • 能说清 read()、lap()、reset() 的区别。
  • 运行一次 LLMGEN_PROFILE=1 zig build run，能读懂算子耗时表和"(其它)"那一行。

原理

一次 generate() 的时间线如下。TTFT 是"用户看到第一个字"的时刻，所以包含 prefill 和第一次 sample，不只是 prefill。

prefill = t(prefill 返回) − t(generate 开始) TTFT = t(第一次 sample 返回) − t(generate 开始) E2E = t(generate 准备 return) − t(generate 开始)

02TPOT / ITL 与分位数入门

目标
记录每两个相邻 token 之间的间隔（ITL），算出 TPOT 和 P50/P90/P99；同时去掉生成结束时一次多余的 forward。

改动清单

文件位置类型内容
profiler/common.zig文件末尾新增percentile、mean
profiler/metrics.zig字段、deinit、reset、onGenToken、tpotNs、decodeNs、print修改记录和输出 ITL
executor.zigdeinit()修改释放 itl_ns
executor.ziggenerate() 循环修改idx == 0 换成 onGenToken；最后一个 token 后直接退出

原理

ITL[i] = t(第 i 个 token 产出) − t(第 i−1 个 token 产出) i ≥ 1 TPOT = (t_last − TTFT) / len(ITL) = mean(ITL) t_last = 最后一个 token(含 eos)的产出时刻

TPOT 是均值，ITL 是分布。均值会掩盖抖动：99 步各 20 ms，偶尔一步 500 ms，均值只变成 24.8 ms，但 P99 和 max 会把它暴露出来。另外，decode 的 ITL 会随上下文变长而缓慢增加，因为注意力要读的 KV 越来越多，所以"前 10% 均值 vs 后 10% 均值"也很有参考价值。

为什么 TPOT 不用 (E2E − TTFT) / (gen_tokens − 1)E2E 的尾部可能包含不产出 token 的工作：
  • 以 eos 结束：eos 那一步的采样时间算进了分子，但 eos 不计入 gen_tokens_len，分母少 1。
  • 以 max_tokens 结束：最后一个 token 产出后，循环还会再调一次 decodeStep，这次 forward 的结果没人用（步骤 6 会把它去掉）。
用最后一次产出的时刻 last_emit_ns 做终点，TPOT 就严格等于 ITL 的均值。

检查点

  • TPOT 和 ITL 均值完全相等（只差整数除法的舍入）。
  • 生成上千个 token 时，"后 10% 均值"明显大于"前 10% 均值"，这就是 KV 变长的代价。

03吞吐 tokens/s入门

目标
输出 prefill 吞吐、decode 吞吐和总吞吐，并理解为什么这两个阶段的吞吐会差几十倍。

改动清单

文件位置类型内容
profiler/common.zig文件末尾新增perSec
profiler/metrics.zigprint() 末尾修改三行吞吐

不需要新的打点，全部用前两章已经记下的数据计算。

原理

prefill 吞吐 = prompt_tokens / prefill_s decode 吞吐 = len(ITL) / (t_last − TTFT)_s = 1 / TPOT 总吞吐 = (prompt_tokens + gen_tokens) / E2E_s

prefill 一次 forward 处理 P 个 token，权重只读一遍，能把算力用满（计算密集）。decode 每次 forward 只处理 1 个 token，却仍要把约 1.2 GB 的权重整个读一遍（访存密集）。所以单序列下，prefill 吞吐通常是 decode 的几十倍。如果你测出来只差几倍，说明 prefill 的矩阵乘没有发挥批量计算的优势，第 6 章可以确认这一点。

2print 末尾输出三种吞吐

注意吞吐要写在 if (itl.len > 0) { ... } 块的外面，否则只生成一个 token 时连 prefill 吞吐也看不到。

04按阶段统计算子，拆解时间账本进阶

目标
(1) 让 OpProfiler 分开统计 prefill 和 decode；(2) 把 E2E 拆成 forward、采样、反分词+打印、其它四部分；(3) 两个开关都开时，算出 decode 阶段的框架开销。

改动清单

executor.ziggenerate()修改切换阶段；循环里计 sample / detok；结尾按阶段打印
executor.zigforward()修改累加 forward_ns

为什么要按阶段拆

原来的算子表把 prefill 和 decode 混在一起。prefill 只跑 1 次但很重，decode 跑上千次但每次很轻，混在一起之后，"LINEAR 占 80%"到底是哪个阶段的就说不清了。而且两个阶段的优化方向完全不同：prefill 要优化矩阵乘（GEMM），decode 要优化矩阵向量乘（GEMV）和访存。

时间账本

E2E = forward_ns + sample_ns + detok_ns + 其它 forward_ns = Σ 算子 ns(OpProfiler) + 框架开销 框架开销 = resolveDims + allocateOutput + resetStepActivations + executeView + Timer 本身 + CUDA sync 等待

四段时间互不重叠，所以加起来不会超过 E2E。"其它"是 onGenToken、append、循环控制等零碎开销，通常很小。

原来的统计表是 op × device，现在外面再套一层 phase。Stat / PerDevice / Table 挪到结构体外面作为文件级类型，后面的 printPhase 和测试都会用到。

2profiler.zig：print 改成 printPhase，新增 opNs

6executor.zig：generate() 的四处改动

(a) prefill 结束后切换阶段；(b) 用一个 step_timer 依次切出 sample 和 detok 的时间；(c) 删掉原来的 defer ... profiler.print(...)；(d) 在结尾按阶段打印，两个开关都开时再打印框架开销。

step_timer 为什么每轮要 reset循环体的末尾是 decodeStep（一次 forward），它的时间已经由 forward_ns 统计。每轮开头 reset()，保证第一次 lap() 只量到 sample()，不会把上一轮的 forward 也算进来。
为什么去掉 defer原来的 defer 会在 return 之后才打印，而且现在要打印两个阶段、还要用到 metrics 里的数据，写在 e2e_ns 之后更直接。代价是 generate() 中途出错时不再打印算子表，这对排查性能问题没有影响。

06算子级 Roofline进阶

目标
给每个算子统计 FLOPs 和访存字节，算出计算强度（AI）和实际达到的 GFLOP/s、GB/s，判断它卡在算力还是带宽。

Roofline 模型

计算强度 AI = FLOPs / Bytes (FLOP/B) 可达性能 = min(峰值 FLOPS, AI × 峰值带宽) 拐点 AI* = 峰值 FLOPS / 峰值带宽 AI < AI* → 带宽受限(memory bound) AI > AI* → 算力受限(compute bound)

以 decode 时的 q_proj 为例：输入 [1, 1024]，权重 1024×2048（BF16）。FLOPs = 2 × 1024 × 2048 ≈ 4.2M，Bytes ≈ 4 MB，AI ≈ 1。常见硬件的拐点都在 10~300 之间，所以 decode 时的 LINEAR 一定受带宽限制。prefill 时 seq = 512，AI 在 400 以上，就变成受算力限制了。

1profiler.zig：Stat 加字段，新增 Cost 和 opCost

默认的估算方法是：字节 = 所有 src 的大小 + 输出的大小，FLOPs ≈ 输出元素数。这对逐元素算子（ADD、MUL、SILU、RMS_NORM）是对的，但有三类算子必须单独处理，否则 roofline 表会给出离谱的数字：

算子src 里有什么默认估算的问题正确的算法
LINEAR[x, W]（见 module/linear.zig）字节没问题，但 FLOPs 远不止输出元素数FLOPs = 2 × 输出元素数 × K，K 取 x 的最后一维
EMBEDDING[input_ids, 整张词表]（见 module/embedding.zig）把 311 MB 的整张词表算成读入，实际只读 token 对应的几行 → GB/s 虚高几万倍字节 = ids + 读出的行 + 写出（读出的行和输出一样大）
APPLY_ROPE[x, cos 表, sin 表]（见 module/rope.zig）cos/sin 表各 [context_length, rope_dim] × f32，Qwen3 的 context_length 是 40960，每张 21 MB，实际每步只用 seq 行 → GB/s 虚高字节 = x + 输出 + 2 × seq × rope_dim × 4B
PAGED_ATTN / FLASH_ATTN[q, 本步的 k, 本步的 v]历史 KV 存在分页池里，不在 src 中，读 KV 的字节完全没算 → AI 虚高约 80 倍FLOPs = 4 × 输出元素数 × ctx；字节另加 2 × ctx × kv_dim × elem
怎么发现估算错了任何算子的 GB/s 都不可能超过硬件峰值（RTX 3090 是 936 GB/s）。看到超过的，用 GB/s × avg_us 反推出每次调用算了多少字节，再和张量大小对比，就能定位是哪个 src 被多算了。比如 EMBEDDING 显示 96032 GB/s、平均 3.2 µs，反推出每次 307 MB，正好是整张词表的大小（151936 × 1024 × 2B）。

prefill 时 attn_ctx 传的是 P，而因果注意力平均每个 token 只看 P/2 个位置，所以 prefill 的 ATTN FLOPs 会高估约 2 倍；decode 时是准确的。KV 字节在 prefill 时也按 P 计算，同样是上界。

为什么 activation 的 used 不是 0forward() 第一次运行时先算持久节点（rope 表），然后调用 markPersistentCursor() 记下每个激活池的水位。之后每层结束时 resetStepActivations() 只回卷到这个水位，不会回到 0。所以 used 停在持久区的大小，peak 才是"持久区 + 单层最大中间结果"。持久区的大小可以直接从 used 读出来，这里是 42 MB。
这份输出暴露的问题：rope 表大了 40 倍rope 表的行数取自 context_length（Qwen3 的 GGUF 里是 40960），见 module/rope.zig。但推理时最多只用到 max_seq_len = 1024 行。结果是：
  • CPU 和 GPU 的激活池里各存了一份 42 MB 的表，占激活峰值的 87%；
  • prefill 时在 CPU 上算这张表要 140 ms（第 4、6 章算子表里的 ROPE_CACHE），再拷到 GPU 又要约 5.6 ms（prefill 的 MEMCPY）。
行数改成 min(context_length, max_seq_len) 后，每份表只有 1 MB，激活峰值约 7 MB，TTFT 约减少 145 ms。
延伸：KV 占用的时间序列想看 KV 占用随步数怎么增长，可以每 N 步把"已用块数"追加到一个 ArrayList，最后打印或写进 JSON。这和第 8 章的"每步快照"是同一种做法。
检查点
  • GPU 权重池的 used = N_mm × 权重字节 + norm 权重字节，精确到字节。对不上就说明有权重放在了别的设备上，或者数据类型和你以为的不一样。
  • activation 的 used = 持久区大小（rope 表），peak − used ≈ 单层中间结果的最大值。
  • KV 已用块数 = 层数 × ⌈缓存 token 数 / block_capacity⌉。
  • 单序列时每层最多只浪费最后一块里没填满的槽位，所以块内碎片率 ≤ (block_capacity − 1) / (已用块数 × block_capacity)，上下文越长越接近 0。
  • 激活池的 peak 出现在 prefill，并随 prompt 长度增长（prompt 越长，单层中间结果越大）。

  • format 相关报错：Zig 0.15 里 std.json.fmt 返回的 Formatter 要配合 {f} 使用，不能用 {} 或 {any}。
  • no field named 'interface'：file.writer(&buf) 返回的是 File.Writer，打印要通过 w.interface.print(...)，最后别忘了 flush()，否则文件是空的。
检查点
  • 同一配置 5 次运行的 TPOT 波动在 ±3% 以内。超出的话，先排查后台负载和温控降频。
  • 改了一个算子之后，能用两个 commit 的 JSON 中位数说明"快了多少、快在哪个阶段"。

建议的落地顺序

  1. 第 1–3 章：拿到 TTFT / TPOT / 吞吐，作为之后所有对比的基线。
  2. 第 4 章：把时间账本拆清楚，往往能直接发现最便宜的优化点（比如每个 token 5 ms 的 top-p 全量排序）。
  3. 第 5–6 章：知道离上限有多远，再决定优化哪个算子。
  4. 第 7 章：调大 max_seq_len 或接入批处理之前必须做。
  5. 第 8–9 章：等 runner/ 路径跑通后接入，同时建立基准脚本，防止性能回退。
